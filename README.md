# E-Mail-Agent

Lokaler Dienst, der mehrere IMAP-Postfächer **nur lesend** abruft, jede Mail mit Jev (OpenRouter, System One `typesafe/jev-1.13`) klassifiziert und die Antworten in SQLite speichert. Ein Review-Dashboard zeigt Ergebnisse und Abweichungen zum Provider-Spamfilter.

**Status: Beobachtungsmodus.** Es gibt keine Produktionsfreigabe. Der Agent verschiebt, löscht, markiert oder beantwortet keine Mails und legt keine Entwürfe an. Die Spam-Quarantäne läuft nur als Shadow-Regel (Kandidat und Entscheidung werden protokolliert, nichts wird ausgeführt). Eine Schreibfreigabe erfordert eine eigene, bewusste Entscheidung nach Auswertung der Beobachtungsphase.

## Lokale Einrichtung

1. Node 26.12.1 exakt (siehe `.nvmrc`), z. B. mit fnm: `fnm install 26.12.1 && fnm use`.
2. `npm install`
3. `cp .env.example .env.local` und `OPENROUTER_API_KEY` eintragen. `.env.local` ist von Git ignoriert.
4. Konten-Datei anlegen: `mkdir -p data && cp docs/accounts.example.json data/accounts.json`, Platzhalter ersetzen, dann `chmod 600 data/accounts.json`. Die Datei ist von Git ignoriert und wird nie ausgegeben oder committet.
5. `npm run dev:live` startet Server, IMAP-Worker und Klassifizierung mit der echten Datenbank (Bindung standardmäßig `127.0.0.1`). `npm run dev` startet dagegen immer mit synthetischen Daten, siehe Abschnitt Entwicklung.

Endpunkte: Dashboard `/`, `GET /api/emails`, `GET /api/status`, `GET /api/health` (offen), Anmeldung unter `/welcome` und `/api/auth/*`. Alles außer Health und Welcome verlangt eine Session (siehe Zugang).

## Zugang über das Tailnet (Tailscale Serve)

Die App bindet immer an `127.0.0.1` (nie `0.0.0.0`). Von außen kommt man nur über `tailscale serve`, das HTTPS im Tailnet bereitstellt (nötig für Service Worker und PWA auf dem iPhone) und die Identität als Header `Tailscale-User-Login` mitgibt. Hintergrund und Quellen: `docs/access-contract.md`.

1. Tailscale auf dem Host und auf dem iPhone installieren, beide im selben Tailnet. HTTPS-Zertifikate und MagicDNS in der Tailscale-Admin-Konsole aktivieren.
2. App starten (`npm run start` oder `docker compose up -d`, Port 3000 nur auf `127.0.0.1`).
3. `tailscale serve --bg 3000` (Hintergrundbetrieb; Status mit `tailscale serve status`, abschalten mit `tailscale serve reset`). **Nie** `tailscale funnel` verwenden: Funnel ist öffentlich und liefert keine Identität.
4. Allowlist anlegen (ohne sie ist niemand zugelassen): `data/auth-allowlist.json` mit `{"logins": ["dein-login@example.com"]}`, `chmod 600`. Bei Docker liegt sie im Volume `/data`, z. B. `docker compose cp auth-allowlist.json email-agent:/data/auth-allowlist.json`. Änderungen gelten sofort, auch für bestehende Sitzungen. Das Geheimnis `auth-secret` entsteht beim ersten Start von selbst (0600, nie committen).
5. Auf dem iPhone `https://<gerät>.<tailnet>.ts.net` öffnen, "Login" tippen, dann "Zum Home-Bildschirm". Die Session gilt 30 Tage; Abmelden per `POST /api/auth/logout`.

`npm run dev` (synthetisch) braucht kein Tailscale: Der Login-Knopf meldet dort als `dev@synthetic.invalid` an.

## Datenschutz

- Gespeichert werden nur Metadaten (Absender, Betreff, Zeitstempel, Ordner/UID) und Jev-Antworten. Kein Mailtext, kein Auszug, keine Rohquelle, keine Roh-Response.
- Mailinhalte erscheinen nie in Logs, API oder Dashboard. Testdaten sind ausschließlich synthetisch.
- Der Lese-Zugriff auf IMAP ist schreibgeschützt (read-only). Einzige Ausnahme: der Schreibport für „Spam als gelesen markieren“ (siehe unten); er setzt und entfernt ausschließlich das Flag `\Seen`.
- Zugangsdaten liegen nur in `.env.local` und `data/accounts.json` (Modus 0600).

## Automatische Aktionen: Spam als gelesen markieren (M7a)

Die Regel „Spam gelesen“ markiert Spam per IMAP als gelesen (`\Seen`); verschoben oder gelöscht wird nichts. Sie greift, wenn Jev `is_spam` positiv sieht (kalibrierte Schwelle, v1: 0.80) **oder** die Mail im Spam-Ordner des Providers liegt und Jev nicht ausdrücklich „kein Spam“ sagt. Mails der Kategorien `security_auth` und `transactional` und Absender auf der Allowlist bekommen nie eine Aktion; bereits gelesene Mails auch nicht. Fehlt oder fehlt die Zuordnung der Jev-Antwort, passiert außerhalb des Spam-Ordners nichts.

- **Modus je Konto** in `data/accounts.json`: `"auto_actions": { "spam_seen": "off" | "dry_run" | "live" }`. Ohne Eintrag gilt **`dry_run`**: Die App protokolliert nur, was sie tun würde (`mailbox_actions`, Status `planned`), und öffnet nie eine Schreibverbindung. `live` muss ausdrücklich eingetragen werden und gilt nach einem Neustart des Servers; dabei werden auch frühere `planned`-Zeilen dieses Kontos ausgeführt (höchstens die letzten 14 Tage, begrenzt durch das Tageslimit).
- **Not-Aus:** Existiert die Datei `auto-actions.disabled` neben der Datenbank (`data/auto-actions.disabled`, im Docker-Volume `/data/auto-actions.disabled`), wird nichts mehr geplant und nichts geschrieben, auch kein Undo auf dem Server (Antwort `409 kill_switch`). Datei anlegen = Stopp (`touch data/auto-actions.disabled`), Datei löschen = weiter. Wirkt sofort, ohne Neustart.
- **Tageslimit:** höchstens 200 Live-Aktionen je Konto in 24 Stunden (`DAILY_ACTION_LIMIT` in `lib/constants.ts`); weitere Mails warten (es entsteht keine Zeile) und werden beim nächsten Start nachgeholt.
- **Rückgängig:** `POST /api/emails/:id/unread` (Session, Veryfront-CSRF plus `x-app-csrf`, Rate-Limit). Live-Konten entfernen `\Seen` auf dem Server, Dry-Run-Konten ändern nur den App-Status. Danach markiert die Regel diese Mail nie wieder. Antworten: `200 { ok, id, mode, seen: false }`, Fehler nur als Code (`404 not_found`, `409 kill_switch`, `502 store_rejected|uidvalidity_changed|imap_error|…`, `503 account_unavailable`).
- **Ansicht:** `GET /api/actions?mode=dry_run|live&status=…&limit=…&cursor=…` liefert `{ actions: [{ id, email_id, account, rule, action, mode, status, failure_code, created_at }], next_cursor, counts }` (nur IDs und Codes, keine Inhalte). Grundlage der Ansicht „Aussortiert“ (`/aussortiert`: Trockenlauf und Ausgeführt, je Mail „Wieder ungelesen“). Undo-Zeilen (`rule = undo`) werden weder gelistet noch gezählt. `GET /api/emails` liefert zusätzlich `auto_actions` (Modus je Konto-ID, nie Zugangsdaten), `GET /api/emails/:id` die Aktion der Mail als `mailbox_action` (nur Codes); der Kopf zeigt „Postfach nur lesend“, solange kein Konto `live` ist.
- **Synthetischer Modus** (`npm run dev`): Die Regel läuft über die synthetische Datenbank, der Modus ist immer `dry_run`, es gibt keinen Schreibport.
- Fehlgeschlagene Live-Aktionen (`failed`, mit Code) werden nicht automatisch wiederholt.

## Briefing und Entwürfe (M6, Backend)

- `POST /api/briefing` (Login, CSRF, Rate-Limit) streamt beim Öffnen der App ein Briefing mit höchstens 3 Bullet Points als Server-Sent Events (Ereignisse `meta`, `delta`, `error`, `done`, siehe `docs/agent-contract.md`, Abschnitt 6). Der Agent `briefing` sieht nur Metadaten der offenen Mails (Konto-Kurzname, Absenderdomain, gezäunter und gekürzter Betreff, Kategorie, Dringlichkeit, Wichtigkeit) und Zähler, nie Mailtexte. Mails mit `addresses_an_ai` nicht klar negativ gehen nur als Anzahl ein. Das Ergebnis liegt 5 Minuten im Arbeitsspeicher; gespeichert werden nur `user_state.last_opened_at` und ein Audit `briefing_generated` (Modell, Latenz, Tokens, Anzahl Mails).
- Ohne Modell (synthetischer Dev-Modus, kein `OPENROUTER_API_KEY`, Agent nicht gefunden oder Fehler) liefert die Route einen festen deutschen Text aus dem Kontext, markiert mit `source: "fallback"`. Die UI muss den Text als reinen Text darstellen (kein HTML/Markdown-Rendering).
- `POST /api/emails/:id/draft` (Login, CSRF, Rate-Limit 10 je 10 Minuten) erzeugt auf Knopfdruck einen Antwortentwurf: Sperre (H11), IMAP-Refetch, Agent `replyDrafter`. Antwort `{ draft, language, tone, needs_human_check, reasons }` mit `Cache-Control: no-store`; der Entwurf wird nirgends gespeichert. Im synthetischen Modus antwortet die Route mit `not_available_in_synthetic`.
- `npm run briefing:probe -- --confirm-live` macht genau einen Live-Aufruf des Briefing-Agenten mit einem fest eingebauten synthetischen Kontext und gibt nur Struktur, Modell, Latenz und Tokens aus (den Text nur mit `--show`). Speichert nichts.

## Feedback und Absender-Regeln (M5)

Alles hier liegt nur in der App-Datenbank; es gibt keinen IMAP-Zugriff. Alle POST-Routen verlangen Session, Veryfront-CSRF plus `x-app-csrf` und unterliegen dem Rate-Limit (Reihenfolge: 401, 429, 403, dann Body).

- **Feedback** `POST /api/emails/:id/feedback` mit `{ kind, value? }`; `kind` ist `spam_correct` („ist Spam“), `not_spam`, `category_wrong` (dann `value` = eine Jev-Kategorie: `spam`, `newsletter_promo`, `transactional`, `security_auth`, `personal`, `business`, `unclear`), `reply_needed` oder `no_reply_needed`. Antwort `200 { ok, id, kind, changed, feedback: { spam, reply, category } }`; `GET /api/emails/:id/feedback` liefert den aktuellen Stand je Thema. Das jeweils letzte Urteil je Thema gilt; Wiederholen ist ein No-op. Das Spam-Urteil zählt je Mail einmal in `senders.marked_spam` bzw. `marked_not_spam`.
- **Absender** (`senders`): je Adresse `mails_seen`, `dmarc_pass`, `jev_spam_count` (Mails, die Jev bei der ersten Klassifikation als Spam sah, kalibrierte Schwelle) und Nicos Zähler. Keine Betreffs, keine Inhalte.
- **Regeln** `GET /api/senders/rules[?include_inactive=1]`, `POST /api/senders/rules` mit `{ match: "address"|"domain", value, kind: "blacklist"|"allowlist", account_id? }` (Quelle `nico`, gilt dauerhaft), `POST /api/senders/rules/:id/deactivate`. Pro Ziel gilt ein Urteil: die Gegenregel wird beim Anlegen deaktiviert. Domain-Regeln gelten für genau diese Domain (keine Subdomains); Freemail-Domains (`FREEMAIL_DOMAINS` in `lib/senders.ts`, z. B. gmail.com, web.de, gmx.de) sind als Domain-Regel nicht erlaubt (`400 freemail_domain`).
- **Wirkung heute:** Allowlist schützt (nie eine Aktion). Blacklist ist nur ein zusätzlicher Grund für „Spam gelesen“ (`\Seen`, Trockenlauf-Standard bleibt); gelöscht oder verschoben wird nichts (kommt mit M7).
- **HITL (E7/E8)** `GET /api/senders/hitl` → `{ candidates: [{ key, match, value, jev_spam_count, mails_seen, dmarc_pass_rate, sample_email_ids }] }`: Adressen mit mindestens 3 Jev-Spam-Urteilen, oder die Domain (Summe), wenn die Urteile von mindestens 2 verschiedenen Adressen derselben Domain stammen; nie Freemail-Domains als Domain, nie mit bestehender Regel. `POST /api/senders/hitl/dismiss` mit `{ match, value }` („nicht jetzt“) fragt erst nach weiteren Urteilen erneut.
- **Jev-State:** `sender_history.user_marked_spam` und `user_marked_not_spam` (nur Zahlen) gehen nur bei DMARC `pass` und nur, wenn eine der Zahlen über 0 liegt, mit (`docs/jev-contract.md`).
- **Kalibrierung:** `npm run calibrate` rechnet das letzte Spam-Urteil von Nico je Mail als Label ein (`spam_correct` = Spam, `not_spam` = kein Spam, vor dem Provider-Ordner) und gibt aus, wie viele Labels aus Feedback stammen.

## Stichprobe und Evaluation

- `npm run sample` zeigt zunächst nur eine **Vorschau** (Anzahl, keine Jev-Aufrufe). Erst `npm run sample -- --account <id> --limit-per-folder 200 --confirm <N>` (N = Zahl aus der Vorschau) ruft Jev tatsächlich auf. Weitere Optionen: `scripts/sample.ts`.
- `npm run eval:jev` führt die Evaluation gegen das synthetische Set `tests/fixtures/eval/email-eval-v1.jsonl` aus (Live-Aufrufe an Jev, verursacht Kosten; erfordert `--confirm-live`, im Script gesetzt).
- Wiederholbare Evals auf öffentlichen synthetischen Datensätzen (Details, Mapping und Statistik: `docs/eval-datasets.md`). Ablauf: (1) `npm run eval:fetch` lädt **alle** Zeilen beider Quellen nach `data/eval-datasets/` (gitignored), entfernt exakte Dubletten und schreibt Klassenverteilung und Revision ins Manifest (`--max-rows N` nur für Tests/Debug). (2) Jede Mail liegt über einen Inhalts-Hash fest in `calib` (30 %) oder `test` (70 %). Dreimal `npm run eval:jev -- --source hf --seed 1 --n 100` (Seeds 1, 2, 3; Standard `--split test --strategy balanced`; Grenze 200 Aufrufe je Lauf, optional `--max-cost <USD>`). (3) `npm run eval:compare` vergleicht die Läufe (Mittelwert, min, max, Standardabweichung je Frage, Gesamtkosten) und schreibt `data/eval-runs/insights.md` (Trefferquote mit 95-%-Wilson-Intervall, Konfusionsmatrix, Precision/Recall/F1, Balanced Accuracy, ROC-AUC, Schwellen-Tabelle, Stichprobenbeschreibung; nur Aggregate und Fall-IDs; Pfad mit `--md <datei>`, `--no-md` schaltet ab). Kalibrierung der Schwellen getrennt: `npm run eval:jev -- --source hf --seed 1 --n 100 --split calib`. Schwellen werden nur auf `calib` gewählt, berichtet wird auf `test`. Laufberichte liegen in `data/eval-runs/` und enthalten nur IDs, erwartete Werte, Antworten, Treffer, Kosten und Stichprobenzähler. Ein Lauf mit 100 Mails kostet laut echter Fixture rund 0,00005 $ pro Mail; Live-Läufe startet Nico.
- Mit `--source hf` schreibt `eval:jev` nach dem Lauf die Fälle samt normalisierten Antworten (und `shadow_quarantine`) zusätzlich in die getrennte Dev-Datenbank `data/dev-synthetic.sqlite`, damit `npm run dev` sie zeigt. Ein erneuter Lauf mit derselben Mail, demselben Fragenset und Modell ersetzt die Antworten (der letzte Lauf gewinnt). Abschalten mit `--no-dev-db`. Die Auditzeile `eval_run` jedes Eval-Laufs (auch des festen Sets) geht ausschließlich in diese Dev-Datenbank; die echte Datenbank wird von keinem Eval-Skript geöffnet.
- `npm run agent:probe -- --confirm-live` macht genau einen Live-Aufruf des Antwort-Agenten (`openai/gpt-6-luna` über OpenRouter) mit einer fest eingebauten synthetischen Mail und gibt nur Struktur, Modell, Latenz und Tokens aus (den synthetischen Entwurf nur mit `--show-draft`). Speichert nichts; erfordert `OPENROUTER_API_KEY` (daraus werden `OPENAI_API_KEY` und `OPENAI_BASE_URL` abgeleitet, falls nicht gesetzt). Kosten laut OpenRouter: 0,10 $/M Input, 0,50 $/M Output.
- `npm run eval:agents -- --confirm-live [--set drafts|briefing|all] [--judge] [--write-dataset]` bewertet Antwort-Agent (12 Fälle) und Briefing-Agent (8 Fälle) live auf synthetischen Fällen mit deterministischen Prüfern (Links, IBAN, Telefon, Injection-Wörter, Bullets, Sprache, erfundene Absender) und optional mit LLM-Judge. Höchstens 25 Aufrufe je Lauf (`--judge` nur mit einem Set), Kosten-/Latenzzusammenfassung, Bericht in `data/eval-runs/agents-<iso>.json` ohne Ausgabetexte; `--write-dataset` erneuert die Gate-Datasets `evals/datasets/reply-drafter__v1.jsonl` und `briefing__v1.jsonl`. Live-Läufe startet Nico. `npm run eval` prüft diese gespeicherten Ausgaben offline; die mitgelieferten sind von Hand erzeugte Beispiele (`origin: derived`) und belegen erst nach Nicos Live-Lauf etwas über die Agenten (Details: `docs/agent-contract.md`, Abschnitt 7).
- Fragenset v2 (`email-classification-v2`, Details in `docs/jev-contract.md`): v1 bleibt Standard, v2 wird ausdrücklich gewählt. `npm run jev:probe:v2 -- --confirm-live` macht genau einen Live-Aufruf mit einer fest eingebauten synthetischen Mail und schreibt `tests/fixtures/jev-email-v2-response.json` (Nico führt es aus). `npm run eval:jev -- --question-set v2 --dataset v2` wertet das schwierigere synthetische Set `tests/fixtures/eval/email-eval-v2.jsonl` (29 Fälle) mit v2 aus.
- `npm run eval` läuft **offline ohne Secrets** (auch in CI) und prüft die gespeicherten Jev-Urteile der synthetischen Sets in `evals/datasets/` gegen die erwarteten Werte (Veryfront `evalDataset`, `metrics.answer.jsonMatch`). Erneuern nach einem Live-Lauf: `npm run eval:jev -- --write-dataset` (Details: `docs/eval-datasets.md`, Abschnitt Offline-Gate).
- `npm run calibrate` liest nur die lokale Datenbank und zeigt je `noul`-Frage die Verteilung (min, p10, Median, p90, max) getrennt nach Provider-Posteingang und -Spam-Ordner sowie Precision und Recall gegen das Provider-Label für Schwellen von 0.50 bis 0.95. Nur Aggregate, nie Betreff oder Absender. Optionen: `--question-set <version>`, `--account <id>`, `--json`.

## Entwicklung

- `npm run typecheck`, `npm test`, `npm run build`.
- `npm run dev` läuft **immer synthetisch**: `DATABASE_PATH` wird auf `data/dev-synthetic.sqlite` gesetzt, IMAP-Worker und Klassifizierung sind aus (auch wenn `ACCOUNTS_FILE` in `.env.local` steht). Die Startzeile zeigt `workers=disabled data=synthetic`. Echte Daten bleiben strikt getrennt; eine Schutzprüfung verweigert das Schreiben synthetischer Daten in jede Datenbank mit Nicht-Synthetik-Konten (synthetisch = Konto-ID `hf-*` und Host `synthetic.invalid`).
- Dev-Daten füllen: `npm run eval:fetch && npm run dev:seed`. `dev:seed` importiert alle geladenen (entdublierten) Fälle beider Partitionen aus `data/eval-datasets/` ohne Jev-Aufruf (kostenlos, wiederholbar): je Quelle ein Konto (`hf-triage`, `hf-sinabis`), Mail mit Fall-ID als Message-ID, Absender `noreply@<Domäne>`, Betreff aus dem Fall, Empfangszeit deterministisch über die letzten 14 Tage verteilt, Ordner `Junk` bei erwartetem Spam/Phishing, sonst `INBOX`. Kein Body, kein Auszug. Ohne Jev-Antworten haben die Mails keine Klassifikation (Dashboard: `-`). Ist die Dev-DB leer, startet die App trotzdem und weist auf diese Befehle hin.
- `npm run dev:live`: bisheriges Verhalten (`.env.local`, echte Datenbank, Worker nur wenn die Konten-Datei existiert). `npm run start` (Produktion/Docker) ist unverändert.
- Im Entwicklungsmodus warnt der Start einmal, wenn Agent-Worktrees unter `.claude/worktrees/` eigene `node_modules` haben: Veryfront überschreitet dann das CSS-Kandidatenlimit und liefert keine Styles. Betroffene Worktrees mit `git worktree remove` entfernen, nachdem ungesicherte Arbeit geprüft wurde.
- Code-Navigation: `graphify query "<Frage>"` bzw. `graphify update .` (Graph in `graphify-out/`, ignoriert; nie `graphify extract`/`add`, um keine Daten zu übertragen).
- Verbindliche Regeln: `docs/IMPLEMENTATION_PLAN.md`, Schema `docs/erd.md`, Abweichungen `docs/DEVIATIONS.md`.
